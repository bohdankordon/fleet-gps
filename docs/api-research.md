# Исследование eQuGPS API

- Дата начала: 2026-08-04.
- Проверяемый endpoint: `GET /devices`.
- Ожидаемая авторизация: HTTP Basic Auth с email и password (по `docs/equgps-swagger.json`).
- Намеренно скрываемые поля: `uniqueId`, `phone`, `contact`, `attributes`, email, пароль, токены и `Authorization`.
- Swagger заявляет формат `date-time` для `lastUpdate`, но реальный API возвращает `YYYY-MM-DDTHH:mm:ss.SSS+0000` (timezone offset без двоеточия), который не проходит строгую ISO 8601-проверку Zod. Транспортная схема принимает непустую строку, `null` или отсутствие поля, а нормализация выполняется отдельно через `Date.parse` с безопасным fallback для локального времени. Формат подтверждён ручной проверкой 2026-08-04.

## GET /reports/summary

- Используемые периоды: текущий календарный день Europe/Kyiv — от `2026-08-03T21:00:00Z` (локальная полночь 2026-08-04) до момента запроса; предыдущий полный день — от `2026-08-02T21:00:00Z` до `2026-08-03T21:00:00Z`. Границы строятся Luxon в `Europe/Kyiv` с учётом DST и отправляются как ISO 8601 UTC без миллисекунд. Динамическая правая граница текущего дня в первых двух неуспешных пробах не была напечатана до HTTP 400; последующие запуски выводят её до обращения к API.
- Swagger заявляет поля `deviceId`, `deviceName`, `maxSpeed`, `averageSpeed`, `distance`, `spentFuel`, `engineHours`; транспортная схема считает обязательным только числовой `deviceId`. Числовые показатели допускают число, `null` или отсутствие поля, при этом отрицательные дистанция и скорости отклоняются.
- Ручные пробы 2026-08-04: `GET /devices` и `GET /positions` завершились до запроса отчёта; `GET /reports/summary` дважды вернул HTTP 400. Тело ошибки не записывалось и не выводилось. Поэтому фактические типы полей, число строк, пробег, нулевые и отсутствующие значения пока не подтверждены.
- Расхождений фактической структуры `ReportSummary` со Swagger пока не зафиксировано: успешного тела ответа не получено.
- Пригодность для пробега одной машины, суммарной статистики нескольких машин и ежедневного отчёта пока не подтверждена из-за HTTP 400.
- Swagger заявляет ответ XLSX для этого endpoint; скачивание и сохранение Excel намеренно отложены для отдельного исследования.

### Контролируемая диагностика HTTP 400

- Использовался один `deviceId` не disabled-устройства со статусом `online` (значение не записывается), предыдущий полный календарный день Europe/Kyiv: `from=2026-08-02T21:00:00Z`, `to=2026-08-03T21:00:00Z`.
- Время передавалось без миллисекунд; использовался `Accept: application/json`; дополнительный `Content-Type` для GET не устанавливался.
- Результат: HTTP 400, `Content-Type: application/json`. Очищенное сообщение сервера: `[redacted] (Summary:42 < *:96 < ReportResource:147 < ...)`. Сервер не сообщил имя проблемного параметра или код ошибки.
- Текущий период строится от начала киевского дня до текущего времени, усечённого до секунды, поэтому `to` не является концом дня и не находится в будущем. Ранее сериализатор мог сохранять ненулевые миллисекунды; это исправлено до диагностического запроса.

## Диагностика content negotiation и исторических отчётов

- Гипотеза: stack trace summary мог означать ошибочный выбор XLSX-обработчика. Для JSON-запросов итоговый `Accept` принудительно установлен как `application/json` после объединения заголовков; `Content-Type` для GET отсутствует.
- Исторический `GET /positions` для одного enabled online-устройства и одного часа предыдущего киевского дня: HTTP 200, 443 ms, `Content-Type: application/json`, `Content-Disposition: attachment` отсутствует, 118 позиций, минимум две позиции подтверждён. Даты поездки и другие данные позиции не записываются.
- `GET /reports/route` для того же устройства и периода: HTTP 400, 139 ms, `Content-Type: application/json`, `Content-Disposition: attachment` отсутствует. Безопасно извлечённый тип исключения: `NullPointerException`; безопасный frame: `ReportResource:102`.
- `GET /reports/summary` в этом запуске намеренно не выполнялся, так как route не вернул успешный JSON.
- Итог: вариант B с оговоркой — исторические positions работают, а обработка report endpoint падает при явном JSON Accept без признаков XLSX. Это указывает на серверную проблему обработчиков отчётов или конфигурации, но окончательно не доказывает её причину.
