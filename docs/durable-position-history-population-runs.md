# Durable position-history population runs (Stage 18A)

Stage 18A provides an internal, durable execution foundation for large, restart-safe GPS history population. It deliberately adds no public HTTP endpoint, browser UI, worker startup hook, poller, scheduler, automatic `SYSTEM` run, rolling maintenance, cancellation, retry queue, retention, or deletion.

`PositionHistoryPopulationRun` persists the exact absolute `to` timestamp, provider-disabled selection, positive window budget, committed-window count, initiator, lifecycle timestamps, lease, and a safe failure code. A run is `PENDING`, `RUNNING`, `SUCCEEDED`, or `FAILED`; its initiator is `USER` or `SYSTEM`. A `USER` run normally references `AuthUser`, and deletion of that user sets the nullable reference to null. `SYSTEM` is foundation for Stage 18C only and creates no work automatically.

PostgreSQL check constraints require `windowBudget > 0`, `committedWindows >= 0`, and `committedWindows <= windowBudget`. A partial unique index permits at most one `PENDING` or `RUNNING` row, while any number of terminal historical rows may coexist. The internal creation service maps an active-row uniqueness race to a stable product conflict; it performs no provider or history work.

The callable worker uses the same PostgreSQL session advisory mutex as Stage 17C and the Stage 14C CLI: key `1706170003`. It first checks whether eligible work exists, then acquires that global lock, re-reads and conditionally claims the run, processes all chunks, and releases the lock in `finally`. Lock contention leaves the run retryable and does not mark it failed. The session lock spans provider work, but no database transaction does.

A `PENDING` claim becomes `RUNNING`, sets `startedAt` once, and assigns a crypto-random UUID lease owner with a 120-second expiry. An expired `RUNNING` lease is recoverable: a future invocation replaces its owner and expiry while preserving `startedAt` and `committedWindows`. An unexpired lease, `SUCCEEDED`, and `FAILED` are not claimable. The active invocation heartbeats every 30 seconds. Heartbeat and terminal transitions condition on run ID, `RUNNING`, and the current lease owner, preventing a stale worker from renewing or finalizing a run it no longer owns.

The worker calls the existing Stage 14C horizon executor in internal chunks of at most 24 committed windows. Before every chunk it re-reads PostgreSQL and computes `remainingBudget = windowBudget - committedWindows`; the next request is `min(24, remainingBudget)`. Durable budgets may therefore be 500, 1,000, 5,000, or another positive safe integer without changing the Stage 17C browser contract, which remains synchronous and limited to 6, 12, or 24. The Stage 14C CLI arguments and output remain unchanged.

The exact crash-safety boundary is the existing Stage 14 window transaction. When the internal durable ownership context is present, that same Prisma transaction inserts/deduplicates observations, conditionally advances the checkpoint, and conditionally increments `committedWindows` by exactly one. Failure of any operation rolls back all of them. An empty provider result still advances a successfully committed window and counts one; failed or already-complete/skipped windows count zero. Legacy browser and CLI runs omit the context, create no durable rows, and update no durable counters.

After each chunk the worker trusts the persisted counter rather than executor totals. It succeeds when the budget is reached, the horizon completes, or a normal chunk makes zero durable progress; the last rule prevents provider-disabled or otherwise ineligible work from spinning. Success sets `SUCCEEDED`, `finishedAt`, clears the lease and failure code, and may finish below budget. An exhausted Stage 14C failure sets `FAILED`, preserves committed work, clears the lease, and stores only a stable safe code. Raw provider responses, URLs, credentials, stack traces, coordinates, fingerprints, sessions, and cookies are never stored. There is no durable job-level retry; Stage 14C retains ownership of provider pacing, Retry-After, and bounded request retries.

If the process dies, no cleanup is assumed: PostgreSQL releases the session lock, the run remains `RUNNING`, its lease expires, and a later callable invocation reclaims the same row. Because checkpoint advancement and durable accounting are atomic, restart cannot under-count already committed work and cannot exceed the database-enforced budget.

Stage 18B may expose large runs in the admin UI. Stage 18C may use the reserved `SYSTEM` initiator for automatic rolling maintenance. Neither behavior exists in Stage 18A.
